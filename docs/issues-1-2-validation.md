## 问题与改动

- [#1](https://github.com/shenyaojin/xXASSXx/issues/1)：终端在输入区上方固定显示当前进展和已等待秒数，从持久的指令、任务修订、模型调用、Codex 工具事件及成员心跳取事实。排队、待确认、执行、结果检查、等待成员/权限和失败分别说明；后台停止、信箱断线另有提示。完成后移除等待区，重开终端可恢复真实状态。不展示内部思维链、原始命令或虚构百分比。
- [#2](https://github.com/shenyaojin/xXASSXx/issues/2)：原代码把发送授权与接收混为一句 CtrlF 提示，并将责任人统一设为发起方。发送方未授权的清单不会出现在接收方文件列表，因而此提示可把接收方引到空列表。现在根据本地收件状态、同一发送方/任务版本的传输事件区分待授权、上传、同步、可下载、接收、失败和撤销；任务卡、附件页及助手上下文共用这些事实。只有实际接收清单存在时才提供本机下载操作，已接收文件须匹配发送方、任务版本和清单。
- 发送方在现有 task protocol 2 中同步附件状态和错误，不新增数据库 schema 或文件传输协议。旧发送端缺少状态时明确说“授权或上传状态尚未同步”，不推断成已可下载。
- 空附件页也列出待交付任务和下一步责任。`a`、`d` 明确标为按键；准备时的附件说明标为历史，当前传输状态另行显示。
- 随后真实跨机实测发现：结果审核模型可能把“等待发送方允许导出”判断成继续执行，从而重复启动 Codex。现在所有候选均为已准备附件时，协调器先等待实际收件，再调用模型审核内容；审核上下文明确提供当前交付事实，不能把候选中的历史 `draft` 当作当前状态。收件并不绕过内容审核。

Issue #2 没有提供原故障任务的两端记录。本次修复并复现了上述通用提示缺陷，未认定其原始文件传输故障一定由未授权导致，也未代为恢复报告人的原任务。
