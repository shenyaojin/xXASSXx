## 团队互信与批准简化（2026-10-15，候选实现，真实跨机器验收进行中）

用户明确产品服务默认互相信任的小团队，认为执行方批准任务后应具备完成任务的能力，不应继续因多层授权反复停顿。用户随后明确授权按此方案实施，并要求真实跨机器完整验收。候选源码已实现，日常客户端与设备权限设置尚未改变。

本轮检查日常 0.8.0 的私有仓库配置任务：执行方已经批准独立目录中的写入/运行，但该模式仍禁止联网和凭据操作，Codex 的实际沙箱也禁用网络；因此生成专用 SSH 密钥并克隆仓库不能按原任务完整执行。执行方提出权限问题后，发起人的聊天回答被保存为补充，待回答问题并未解除；模型却回复“已继续”。这是批准范围、权限问题归属和状态答复的问题，不能仅归因为模型能力不足，也不能将普通补充记录当作任务恢复证据。本轮未提交问题答案、修改设备权限或恢复该任务。

候选实现保留 Ask for approval 与 Full access：前者由执行方一次批准任务所需的本机读写、运行、联网、依赖安装、凭据生成/使用及指定成果发送，后者按本机已有选择自动提供同样能力。默认任务目录用于产物和日志，不再限制任务明确要求的其他本机路径。只读、路径和执行顺序要求仍有效；凭据使用不等于允许发送私钥。local agent 上下文、Codex 实际执行环境与附件发送统一使用有效任务授权。

个人 schema 12 仅为执行授权增加完整范围标记；旧记录默认保留受限权限，不自动扩大历史批准。执行方可在没有活动执行时明确重新批准旧任务。新版本任务仍需批准，普通问题回答保持任务版本不变。

普通聊天可回答发送当时的明确待答问题：保存问题/版本绑定，模型只识别回答意图，内核验证并保存用户原话、提交答案及唤醒执行。状态询问不会作为答案；多个待答问题不会被一个回答全部解除。活动任务的聊天状态由实际记录生成；答案提交、执行方接收与准备续接分开，团队动态同样区分这些阶段，附件传输或补充信息不解除业务等待。执行端问题可携带指定的阶段成果附件，用于先交付公钥、等待外部配置、再继续克隆的同一任务。

Linux 完整自动回归 197 项通过、0 失败、3 项既有忽略，格式、Clippy 和优化构建通过。真实 Lakota 发起、Trader 执行测试进行中，两端保持 Ask for approval；尚未据此宣称端到端验收完成。详见 [访问模式与聊天接续](access-modes.md)。

## 产品理念与第一批用户

开发者正在组建一家以人少而精为特点的创业公司，主业是地球物理相关的软件与服务。团队自己就是 xXASSXx 的第一批用户。xXASSXx 是为主业中的协作需求产生的副产品，先服务内部真实交付，成熟后可以考虑对外销售；当前没有把它确定为独立主营业务，也没有验证外部付费需求。

用户的长期判断是：由少数专业成员组成、每个人都有强大 agent 辅助的小团队会越来越普遍。这是指导产品的假设。xXASSXx 希望让这些成员各自的 agent 在授权范围内交换工作进展、文件与成果，把必要上下文交到下一位成员手里，减少人工催进度、转述、找文件和仅用于同步状态的会议。人的专业判断、客户沟通和关键决策仍需保留。

理解产品时，应从多位真实成员之间的工作衔接出发，覆盖研究、开发和服务交付，而不局限于同一代码仓库中的多个编程 agent。文件管理、脚本管理、消息和任务状态都服务于这个目标；不要仅把项目定位成文件搜索器、网盘、聊天工具或单人多 agent 调度框架。

### 什么是高品质沟通

一次有效交接应让接手者知道：

- 原始需求是什么，谁负责，当前进展和阻塞在哪里。
- 使用了哪一版数据、脚本和参数，相关材料在哪里、允许怎样访问。
- 产生了什么结果，依据是什么，哪些检查已完成，哪些结论仍不确定。
- 下一步需要谁做什么，以及哪些事项需要人来判断或确认。

例如，某成员完成一轮分析后，下一位成员的 agent 能取得获准访问的结果与必要上下文，明确版本和局限，再继续准备后续工作；相关成员可以了解进展而无需反复询问。这是目标体验，不表示已经实现自动连续交接；实际科研程序执行见下方既有部署记录，新增文件交付见本轮附件能力与发布记录。
