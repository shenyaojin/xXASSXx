# 附件交付：使用与实现

更新：2026-10-07（America/Denver）。0.3.0-alpha 提供本功能，个人端迁移至 schema 9，附件协议为 1。双方个人端与团队信箱需一起升级，使用方式如下。

## 日常操作

### 直接发送自己选中的文件

按 **CtrlF → n** 选择接收成员，Enter 进入本地目录，空格勾选，**CtrlS** 发送。发送的是此刻保存的固定副本；以后修改原文件不会改变已发送附件。这个操作本身就是对所选文件和接收人的授权，不调用模型。

CtrlF 可以查看附件批次，Enter 查看详情。列表区分等待允许、上传中、等待对方收取、接收中、已保存到本机、已保存到对方电脑、暂停、撤销与过期。“已保存”来自完整文件校验与接收回执，不代表对方已经阅读。

详情页：

| 操作 | 按键 |
| --- | --- |
| 允许发送助手已准备的固定文件 | a |
| 下载较大的附件 | d |
| 重试暂停的传输 | r |
| 撤销发送 | x |
| 选择文件 | ↑ / ↓ |
| 打开已收到的常见文档、图片、表格 | Enter / o |
| 另存为指定完整路径 | s |
| 用选中的附件继续只读分析 | c |

另存为不会覆盖同名文件。未知或可执行类型只显示保存位置，不自动执行。Linux 没有桌面环境时使用保存路径。撤销会阻止继续从信箱下载，无法收回已经收到的副本。

### 请对方发送已有文件

例如：`@bob 请把这次测试的结果 CSV 和图片发给我。`

发起方确认任务后，由对方自己的 Codex 在其已允许读取的范围内查找。文件不必转换成文本。对方得到明确的文件清单后，在 CtrlF 详情页按 a 允许发送；目录白名单本身不授予导出权限。发起方真正收到文件之前，业务任务保持等待。

自己的助手也有 `prepare_file_send` 工具：对话中已经明确的本地路径可以准备为待确认附件。未知路径仍需先由 Codex 查找，再选择发送；当前以文件选择器作为最确定的直接发送入口。外部 @ 继续表示请求对方处理，不把它当成本地文件发送指令。

### 交付任务产生的文件

明确要求“生成/运行，并把实际结果文件发给我”。执行方在 **CtrlT → Enter** 的本地授权页，除了开放本任务独立目录，还可以单独选择“允许交付本任务结果附件”，默认关闭。

允许后，Codex 把结果引用列入 `deliveries`，Rust 只接受本任务目录内的选定产物，保存副本并发送。读取依据仍放在 `files` 中，不会把所有引用或整个工作目录都上传。没有预先允许导出时，产物保持待允许状态，可在 CtrlF 单独批准。授权只对应本任务当前版本。

执行成功、文件发送成功、对方接收成功分别记录。程序已经成功时，等待文件传输不会要求重新计算。文字审阅通过但文件尚未收到时，保存审阅结果，接收完成后自动结束任务。

### 收到文件后继续处理

附件详情选中文件，按 c 输入问题，然后 CtrlT 查看任务并按 CtrlS 确认。新的分析任务只读取选中的固定副本，不把附件目录加入永久白名单。文件内容属于待分析资料，不授予新权限。

当前快捷入口是只读分析。要修改或运行收到的内容，先另存到自己的工作位置，再按现有流程创建执行任务并开放独立目录。尚未提供附件多选后直接进入写入任务的专用界面。

## 命令行

```sh
xxassxx client files send --to bob --note "本次测试结果" ./result.csv ./figure.png
xxassxx client files list
xxassxx client files show TRANSFER_ID
xxassxx client files allow TRANSFER_ID
xxassxx client files receive TRANSFER_ID
xxassxx client files retry TRANSFER_ID
xxassxx client files revoke TRANSFER_ID
xxassxx client files save TRANSFER_ID FILE_ID /absolute/path/result.csv
xxassxx client files allow-task TASK_ID --revision 1
xxassxx client files preferences --auto-receive 20971520
```

`show` 给出文件编号、大小、校验值、状态与本地路径。`--id` 可用于重复发送请求的幂等标识；`--replaces OLD_ID` 表示新版本关系，每次仍是独立的固定副本和授权。后台自动同步；`files sync` 用于没有运行后台时手动推进，不能与同一数据库的后台并行抢占同步锁。

## 默认限制与存储

| 项目 | 默认值 |
| --- | --- |
| 单文件 | 1 GiB |
| 每批 | 40 个文件，合计 2 GiB |
| 自动接收 | 合计不超过 20 MiB 的附件批次 |
| 分块 | 8 MiB，每次同步每方向最多推进 4 块/附件 |
| 信箱未清理数据额度 | 每发送成员 5 GiB，团队 20 GiB |
| 信箱保留期 | 发起上传起 7 天 |
| 完整接收后的信箱保留期 | 24 小时 |

个人端 `files preferences` 可以设置 `--max-file`、`--max-batch`、`--auto-receive`，单位字节。信箱配置可用 `[transfers]` 设置 `max_file`、`max_batch`、`member_quota`、`team_quota`、`retention_secs`、`receipt_retention_secs`。配置必须满足大小与额度关系；个人端不能绕过信箱限额。磁盘不足时保留进度并暂停。

个人端字节存于数据库同级的 `*.file-transfers`；只读附件分析副本存于 `*.attachment-inputs`。信箱二进制数据存于 `*.attachments`，数据库只存清单、授权、进度与回执。应用和执行助手的普通读取范围排除这些私有目录；选定附件分析通过独立范围开放。本机副本目前保留，不随信箱到期自动删除。

信箱按现有鉴权与 HTTPS 传输，服务器可以读取文件字节；本版没有端到端加密。二进制流量使用独立 `/v1/files` 接口，不进入模型上下文，不塞进旧文本消息。新附件任务会等到接收成员注册附件能力后才派发，老成员的普通文本任务仍可使用。

上传和下载分别保存分块进度。块与整文件都校验 SHA-256，收到后通过临时文件落盘、同步、改名，再记录接收结果并回执。重启可以续传，重复块和回执幂等。文件内容、大小、身份或清单不一致会拒绝；源文件复制期间改变时要求重新选择。拒绝符号链接、特殊文件、路径越界和应用凭据。

## 实现入口与验证

- `src/transfers/`：固定文件清单、本地权限与存储、后台传输、信箱接口。
- `src/schema_v9.sql`：增量迁移，不重建已有身份和历史。
- `src/task_coordinator.rs`、`src/native_tasks.rs`：已有文件交付、结果产物和接收完成条件。
- `src/tui/mod.rs`、`src/app/model.rs`：终端操作与助手准备附件工具。
- `tests/transfers.rs`、`tests/task_workflow.rs`：授权、校验、恢复、兼容与任务完成回归。

实际操作、真实模型证据和已知边界见 [本轮验收](file-transfer-validation.md)。本版不包含目录实时同步、直接改对方原文件、自动执行收到的文件、后台无限接续，也没有新增专门的附件 MCP 工具。
