## 角色合同

新任务保存显式角色合同：发起人沿用任务身份；`roles.executor` 是当前唯一执行成员；`roles.recipients` 是成果接收人；`roles.others` 是其他参与者。当前日常路径支持一位执行者和一位成果接收人，数据保留数组形状以描述角色。参与关系由发起人、执行成员及其他参与者组成；仅收成果的成员不收到任务提议、执行上下文或私人历史，也不会获得执行作业。

每台机器仍只管理自己的读取范围、执行授权和发送授权。本机与远端切换使用相同的分配协议；新执行版本不会复制旧成员的批准。执行上下文明确当前角色，物理路径按执行端自己的目录解释，发起方目录不能成为远端文件授权。

新执行端只接收当前要求、发起人的有效补充和精简分配说明（旧执行成员、变更原话、停止确认编号与状态）。`side_effects_checked=true` 表示旧端已完成停止及副作用核对，不是再次询问用户的理由。停止副作用核对详情、旧批准和旧成果不随新提议发送；该说明仅用于显示，不替代本机停止控制状态。纯文字成果发给仅收成果的成员时，封装为独立 `result.txt`，沿用发送端批准与实际接收核验，不暴露私人任务上下文。

## 修订与纠正

- 同目标、同权限的事实补充进入第一阶段的输入与消费记录，不改版本，不撤销已有批准，不解除问题或技术阻塞。
- 执行归属修正保留当前任务编号、原话和历史，产生新执行版本，并明确记录被替代的角色及用户原因。同目标换人时，发起人的有效补充保留原话并建立来源映射；新执行者另建接收和读取记录，不继承旧读取回执或批准。
- 目标、交付物、材料范围或授权范围变化产生新修订。保存完整的当前有效要求和用户原话；原修订保留，不靠持续拼接旧要求表达当前目标。旧模型草稿和旧发现是历史证据，不是用户事实。
- 仅改变成果接收人增加独立的交付代数，不重开计算。当前固定产物可以重新准备给新接收人，文件名、字节和哈希受核验；旧批次和已送达事实保留。新的发送按发送设备的当前授权处理，旧任务发送批准不覆盖新的接收人。已经结束的任务保留实际送达事实；需要另发时由附件入口明确选择。授权表单绑定打开时的角色，执行或收件安排变化后必须重开。

自然语言继续由 local agent 识别；确定性出口为 `/roles`：输入 `执行 @成员 原因` 或 `接收 @成员 原因`。本机执行使用发起人自己的成员名。`/handoff` 在原执行端填写已核对的副作用、保留成果和安全边界。

## 停止屏障

已确认的分配发生修订时，发起端先持久保存停止请求并冻结旧分配。接收端的停止记录可以先于迟到的任务提议存在，防止旧消息再次启动执行。运行校验、结果提交和附件发送都受分配与版本约束。

信箱明确证明旧提议从未接受时，在同一事务保存撤销墓碑和停止证明，迟到重试不能复活旧分配；已接受、响应丢失或状态未知时不能走这条捷径。没有启动记录的旧分配可在原执行端确认没有在途执行后自动应答。已有运行记录时，先等待执行进程和清理锁释放，再要求原执行端核对副作用，通过 `/handoff` 保存依据。进程退出本身不代表外部副作用已核对。

发起端收到绑定原任务、版本与执行者的停止确认后，才派发新版本。离线不等于已停止；等待时明确表示旧执行状态尚未确认。迟到的旧结果只保留历史，不能完成新版本。已发生的文件修改、外部操作和已送达文件不会因角色变更而回滚。

## 迁移与兼容

个人库从 schema 13 增量迁到 14：新增任务及修订的角色字段、角色变更记录、停止记录和交付批准代数。旧任务的角色字段为 NULL，继续原合同和原多成员历史；不追溯扩大授权，也不推断其参与者现在只应收成果。要改变旧合同的角色，应创建有明确角色的新任务。

信箱增量迁到 schema 4，记录显式角色能力和停止协调。客户端通过身份接口与心跳协商 `task_roles_protocol=1`。新角色任务仅派发给近期在线且声明支持该协议的执行参与成员。旧信箱或不支持新角色的执行端明确等待升级，不将新任务降级为按参与者推导执行者。普通成果接收仅使用既有附件协议，不因此获得新角色执行合同。

本阶段不自动安装任何迁移到日常目录。升级仍须遵守停服与可恢复备份流程。

## 后续阶段接口

后续工作应保留 `roles`、执行 `revision`、`delivery_generation`、停止请求编号和核对依据。新自动化不得绕过停止屏障，不能从运输 ACK、在线心跳或任务状态推断副作用安全。继续使用第一阶段输入 ID、问题绑定、读取回执、运行 ID 与恢复预算记录。

成果来源应关联执行成员、任务版本、运行及实际文件哈希。授权检查必须发生在执行或发送的那台设备；任务角色和模型文字都不能授予另一台设备权限。
