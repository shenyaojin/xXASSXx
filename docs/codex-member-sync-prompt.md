# 团队成员自动同步与 Nightly 发布提示词

请在当前 xXASSXx 仓库实际实现团队成员自动同步，完成验收后发布包含该功能的 nightly 预发布版本，并将相关代码推送到 GitHub。先阅读 `AGENTS.md`、`docs/current-state.md`、`docs/debugging.md` 和 `docs/releasing.md`，检查工作区和远端状态，保留已有工作。

## 一 要解决的问题

目前邀请 JSON 带有静态 contacts，个人端安装时将它存入本地。服务器新增成员后，先加入的人不会自动认识后来加入的人；修改服务器邀请文件或重新发送 JSON 也不会更新已经安装的客户端。这会导致成员列表、@ 候选、消息来源校验和实际协作出现不一致。

目标是：任何成员先安装、后安装都可以自动看到当前团队里的其他成员，无需重新安装、重新导入邀请、改配置或手工编辑数据库。邀请中的 contacts 只作为首次启动或兼容旧版时的缓存；团队信箱提供经过身份验证的权威成员名单。

截至本提示词准备时，现有团队为 owner、pengchao、test、mba。pengchao 邀请的本地新版已经包含 owner、test、mba，私人文件位于下载目录中的 `xXASSXx-发给朋友/pengchao-updated-20261007.json`。不要把这些用户名写死到产品逻辑，不要读取、打印或提交邀请凭据来编写测试。

## 二 服务端成员目录

增加经过现有成员凭据认证的完整成员目录接口，例如 `GET /v1/members`。只返回必要信息：团队标识、当前成员的 member_id 和 display_name，以及适当的版本或获取时间。禁止返回 token、token_hash、credential_env、密钥路径、其他人的邀请或个人端配置。

名单来自服务端实际有效的成员登记，与身份校验、消息路由使用同一份数据。包含离线和从未上线的已注册成员，不能只把在线心跳列表当作联系人。在线状态仍由现有 presence 机制负责。

沿用现有入队和管理方式，本轮不要求开发注册平台或复杂权限系统。成员新增、显示名变更、退出之后，客户端应在下一次有效同步中反映变化。仍保留身份校验；“自动同步团队成员”不是允许陌生消息自报身份加入联系人。

接口与个人端采用可兼容的增量协议。完整验证响应后再应用；请求失败、认证失败或响应不完整不等于团队成员全部被删除。旧服务端缺少新接口时，个人端保留邀请或既有名单，明确显示尚不支持自动同步，不声称已经取得最新名单。

## 三 个人端自动更新

在启动连接、断线重连和后台定期刷新时同步成员。建议后台默认每 15 秒检查一次，可配置，复用现有 HTTP 客户端与后台调度，不调用 LLM，不阻塞 TUI 输入，也不为每次按键发起请求。

同步前核对团队绑定，验证成员 ID 格式、显示名、唯一性、人数限制和本人记录等必要完整性条件。本人的记录用于验证身份，不把自己作为外部联系人。

在一个一致的本地更新中保存完整有效名单，刷新界面、@ 候选、local agent 上下文、消息发送与接收校验所使用的数据。不要形成“界面已看到，但发送时仍报未知联系人”的两份名单。

重点要求：

- 旧邀请初始化的个人端也能自动补齐新成员，不要求重新 init。
- 保存同步时间和状态。失败时保留最近一次有效结果，界面区分成员离线、名单暂未更新、连接失败和旧服务端不支持，不把暂时离线解释成退出团队。
- 名单应用必须幂等，响应乱序或失败重试不能用旧结果覆盖新结果。不要为了去重引入不必要的复杂基础设施。
- 只更新与成员缓存相关的数据。保留本人身份与凭据、模型和 Codex 配置、白名单、工作目录、会话、任务、文件快照以及执行授权。
- 当前 `identity.config` 内嵌 contacts，另有 contacts 表和 member.toml。先确定单一的有效来源及兼容策略，防止随后读取旧 TOML 把已同步名单覆盖回去；不允许借此覆盖模型或执行设置。
- 显示名更新不改变成员 ID，不把历史消息搬给其他成员。成员退出后保留历史会话、任务和结果，在旧任务上清楚说明该成员已不可用，不再派发新工作；不能删除旧证据或进入无休止重试。
- 同步团队名单不扩大本地目录权限，也不自动授予写入或运行权限。

应在收取和校验新消息之前尽可能完成同步。遇到未知发送者时，可以从已认证的团队目录进行一次受限刷新，再重新校验并处理同一条持久消息；不能仅根据消息内容增加联系人，也不能先丢弃消息或提前 ACK，导致合法新成员的首条请求永久丢失。重复同步和重试不能重复创建任务或启动 Codex。

新成员出现在服务器后，已经运行的 TUI 应自动看到该成员。查看名单、@ 补全、发起任务、接收回复和会议参与者显示必须一致。本轮不增加 slash 命令。

## 四 衔接现有代码

重点检查 `src/mailbox.rs`、`src/team.rs`、`src/presence.rs`、`src/app/daemon.rs`、`src/app/mod.rs`、`src/app/bridge.rs`、`src/tui/mod.rs` 和 `src/setup.rs`，以及涉及任务成员检查的模块。

现有 `Store::contacts()`、`MemberConfig.contacts`、`configure_member()`、`presence::heartbeat()` 和消息来源校验已经构成现用路径，应统一改造，不另建一套仅用于展示的名单。心跳当前会忽略本地联系人中不存在的成员，因此仅在服务端增加 presence 字段不能自动解决整个问题。

保留旧邀请格式的兼容性。无需为了这一个问题废弃用户手里的邀请或旋转已有 token。邀请 JSON 是私有配置，不放入 Git、发布说明或安装包。

如需数据库迁移，使用增量方式保留数据，明确处理旧名单如何成为初始缓存。服务端和个人端分阶段升级时要能解释真实能力，不将旧版的静态名单误称为已经同步。

## 五 验收

补充与实际风险相关的回归，至少验证：

1. A 和 B 先安装，随后服务器新增 C；A、B 无需改邀请、重启或重新安装，在约定刷新时间内看到 C，C 也能看到 A、B。
2. 使用加入 C 之前的旧邀请新装另一份隔离个人端，连接服务器后自动补齐 C；离线启动时保留缓存且不声称最新。
3. @ 候选、普通联系人显示、local agent 上下文和收发校验采用同一名单；新成员的首条消息在名单尚未刷新时不丢失、不被盲目信任，也不重复执行。
4. 服务端更新显示名或移除成员，客户端按下一次有效完整结果更新。短暂离线和 HTTP 错误不清空联系人；历史消息、旧任务和证据保留。
5. 错团队、重复 ID、非法成员、缺失本人、超限和不完整响应被拒绝，原有有效名单及其他配置保持不变。
6. 旧服务端不支持接口时可以继续使用缓存并显示限制；401/403 与普通网络故障得到正确区分，不悄悄信任过期身份。
7. 重启、重连、多次同步和重复消息幂等，正在运行的任务不受无关名单更新干扰。更新前后核对模型设置、执行设置、白名单和身份未被覆盖。
8. 成员目录接口不泄漏凭据，未认证的请求不能读取名单；不会因为自动发现成员而开放额外本地文件或写入权限。

按照仓库的真实终端验收要求，实际打开至少两个独立个人端的 TUI，先保持旧名单，再通过隔离服务器的正常成员登记路径加入新成员。亲自看到旧 TUI 自动出现新人及 @ 候选，并从其中发起一项小型只读任务，经真实 local agent 和 Codex 得到有意义的最终答复。不要手工改个人端 contacts 表制造“自动同步成功”，也不要只凭后台任务 completed 宣称验收通过。

可以用临时团队、合成材料和独立数据库，复用已有合法的 DeepSeek 与官方 Codex 配置。不要冒充真实用户向 pengchao 发测试任务。原生窗口不可用时使用真实可交互 PTY 并保存画面，区分模拟回归、真实终端、真实模型和真实跨机器证据；未完成的实测明确记录。

## 六 Nightly 发布与 GitHub 推送

用户已经要求本功能完成后作为 nightly 版本发布并推送 GitHub。不要把只更新邀请或写提示词的版本发布为“已修复成员自动同步”。

沿用 `.github/workflows/release.yml` 和 `docs/releasing.md` 的三平台构建及校验流程。当前已发布 `v0.2.0-alpha`；实现时先检查远端和已有版本，选择新的、不覆盖历史标签的 nightly 版本，例如 `0.2.1-nightly.YYYYMMDD.1`。日期使用实际发布时的 America/Denver 日期，同日已有版本时递增末尾编号。Cargo.toml、Cargo.lock、本程序输出、标签和发布说明必须一致。

这是本次 nightly 预发布，不要求配置每天自动发版的定时任务。保留既有 Alpha Release，不强制改写历史标签或已有远端提交。

提交前检查全部差异和暂存文件，只提交本次功能、测试、必要文档与版本变更，保留无关工作。特别核对没有邀请 JSON、真实 token、个人数据库、原始模型日志、私人目录材料或 dist 产物进入 Git。同步更新接续摘要、用户升级说明与公开版本说明。

工作区另有已验证的结果检查错误修复，记录在 `docs/review-decision-fix.md` 和对应证据文件中：按阶段约束与校验模型决策，并对错误决策有界重试。后续 Nightly 应一并包含该修复及其回归，保留相关改动；不得把先前真实验收说成针对新 Nightly 二进制重新执行过。

运行相关测试和真实验收后，按发布规范完成格式、Clippy、完整回归及优化构建。正常推送代码和新标签到当前仓库的 GitHub 远端；出现并行改动时保留双方工作，禁止通过强推消除冲突。

等待 Apple Silicon macOS、Intel macOS、Linux x86_64 musl 三个平台的发布构建全部通过。检查三份安装包、SHA256SUMS 和安装器，确认下载与隔离安装、程序版本一致，然后将草稿 Release 发布为 prerelease，标题明确标注 Nightly。不要将它冒充稳定版本或设为稳定 latest。

CI 失败时修复真实原因，不降低验收条件。外部权限或环境阻塞时，说明代码、标签、构建和 Release 各自完成到哪一步；推送标签不是已发布，某一个平台成功也不是完整发布。

本次发布不等于替换所有现用电脑的二进制。说明服务器与个人端如何升级，以及需要升级哪些端才能得到自动同步；实际部署沿用用户对目标机器的授权，不能声称未升级的旧客户端已经自动获得新功能。

## 七 最终交付

交付可运行的成员同步功能、回归与真实终端证据、迁移和兼容说明、新的 nightly 安装包及公开 GitHub Release。最终用中文简要说明旧用户何时能看到新人、邀请是否仍需改动、实际验证范围、提交和版本链接，以及尚未升级的机器或未完成的环节。

请实际完成实现与验证，不停留在计划或复述本提示词。普通实现选择自行判断，不重复询问已经明确的推送和 nightly 发布授权。
