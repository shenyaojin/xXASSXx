# 调试与终端验收流程

更新：2026-10-07。适用于开发者及参与本仓库维护的 agent。

## 先确认用户真正卡在哪里

先阅读 `docs/current-state.md` 并查看工作区状态，保留已有修改。记录用户原话、任务编号/版本、发起与执行成员、实际二进制版本。将终端上看到的状态与同一任务的消息、授权、协调记录、Codex 执行和真实文件对照，不把“消息已发出”“程序退出”和“任务完成”混为一谈。

优先复现原任务的故障，沿实际链路定位原因：发起方界面 → 本地后台 → 信箱 → 执行方后台 → 执行方 Codex → 结果回传 → 发起方答复。修复状态转换、归属、权限或数据处理等通用逻辑；不得根据示例句子、成员名、目录名或科研项目添加专用分支来让一次演示通过。

## 哪些改动必须亲自看终端

以下问题，必须实际启动 xXASSXx 终端界面操作并观察完整任务，不能只跑自动测试：

- 界面显示错误、任务看起来卡住、确认后没有继续。
- 任务被交回错误成员、在错误机器或目录执行。
- 本地授权、远程接续、取消、恢复或结果回传发生变化。
- 最终答复没有意义、难懂，或者与文件和执行记录不一致。

在用户已授权的机器与范围内执行，不重复索要已有许可。使用正在验证的二进制启动；需要观察接收端时，通过执行方自己的终端检查，不能绕过产品直接完成业务操作再冒充产品跑通。原生终端窗口无法操作时，可以使用实际系统 PTY 启动真实程序、发送按键并采集屏幕。明确记录使用了哪种方式；PTY 不等于接管用户已有窗口。

## 一轮完整验收

1. 在发起方终端输入一个自然语言任务，检查执行成员、需求和确认内容。涉及跨成员故障时走真实信箱；适合小规模验证的业务使用可核对的小数据。
2. 确认后继续观察，界面应准确说明正在做什么、轮到谁处理。等待授权不能显示成无原因失败，也不能偷偷启动执行。
3. 涉及写入/运行时，在执行方终端按 CtrlT、Enter 查看本任务的目的、版本、目录和只读范围，选择“允许并开始”。验证发起方无需重试即可继续；取消、暂缓及旧版本授权的边界由相关回归覆盖。
4. 亲自等到发起方终端出现最终答复，再读完整段答复。检查它是否回答原始问题、是否指出真实产物，以及有没有把猜测写成事实。不要在“已排队”“正在处理”或后台显示成功时结束验收。
5. 独立核对必要文件、日志、实际执行成员与次数。写入任务检查实际生成文件；计算任务用可核验的输入/输出验证关键数值。不得改数据库补造成功，也不得用 SSH 直接代做任务来掩盖产品故障。
6. 如果有卡住、绕过产品才能继续、答复误导或无意义，保留失败证据，修通用原因，再走同样的用户操作复验。最后检查任务卡：完成后没有遗留“等待”，目录与成员归属准确。

答复面向普通用户：先说做成了什么，再给少量有意义的数值和必要限制。内部状态名、对象编号、环境变量和完整运行细节放到可展开记录或报告。易懂不能以改写事实为代价，例如未给定地理坐标系时不能把模型 x 方向解释为东西方向。

## 自动检查与证据

为确认的逻辑缺陷增加能覆盖通用条件的回归，优先验证错误机器/版本、授权前后、重复事件以及取消/恢复等边界；避免只断言实现细节或复刻那一个例句。先跑相关测试，发布前运行完整测试、格式检查、Clippy 和发布构建。相同代码在相关检查已通过后，不无故反复扩大测试。

在 `smoke-output/` 保存原始终端画面、执行事件与本地详细核对；可提交的精简记录放到 `docs/`。至少记录任务/版本、两端身份、构建或二进制哈希、操作步骤、失败与恢复、最终答复、实际运行及产物核对结果。不得提交密钥、邀请或个人数据库。分别说明：

- 模拟回归通过了哪些路径。
- 真实终端上实际看到了什么。
- 真实模型、跨机器或业务计算是否本轮重新运行。
- 仍未验证或未修复的事项。

仅修改文档、版本号等不改变运行行为的内容时，不必重复昂贵业务计算；保留已有真实证据并明确其版本，验证新构建的版本、安装和终端入口即可。测试被默认跳过不等于测试通过。若工具或外部环境使终端验收无法完成，记录具体原因，并明确本次尚未完成验收。
