# xXASSXx 执行端 Codex 技能设计

日期：2026-10-14（America/Denver）。源码技能包版本：0.1.3；公开 0.7.0-alpha 包仍携带 0.1.2。

**状态：已实现构建嵌入和每轮加载；真实 DSS 取图、位置清单、只读分析、运行后接续交付与收到脚本只读分析均已有完整验收。** 三个技能保存在仓库 `skills/`，随二进制分发；不安装进开发者的全局 Codex。应用显式提供这些指令，不声称使用 Codex 原生技能自动发现。

0.1.3 对齐无文件答复的合同：非文件问答和没有匹配材料的说明可用 `files:[]` 提交，不需要编造引用或为填清单追问用户。实际文件内容分析仍先选材料、冻结，再读固定副本。本轮真实能力问答与隔离写入验收见 [聊天错误验收](chat-errors-validation.md)，源码尚未发布，不改写此前 DSS 的版本证据。

0.1.2 新增对本机 Full access 的明确处理：当前执行合同可允许原文件修改及联网，发送由本机预授权自动完成；Ask for approval 保留独立目录和发送确认。既有 DSS 验收使用 0.1.1，其历史记录不改写为新版本。模式与边界见[访问模式](access-modes.md)。

## 三个技能的职责

| 技能 | 何时使用 | 具体产出 | 不接管的职责 |
| --- | --- | --- | --- |
| [xxassxx-task-intake](../skills/xxassxx-task-intake/SKILL.md) 接任务与澄清 | 每轮首次启动、恢复、显式重试、切换阶段时；工作中遇到必要信息缺口时 | 读取最新任务，分清执行编号与业务编号，核对当前范围及已有答案；继续工作或提交可回答的问题 | local agent 的草拟、用户确认、跨成员协调 |
| [xxassxx-task-execution](../skills/xxassxx-task-execution/SKILL.md) 执行和结果核验 | 取得本轮任务上下文后 | 按模式/阶段找到材料、分析实际内容、选定发送文件，或按本机访问模式获准的范围运行并检查产物 | 授权、调度、文件运输、自动重放 |
| [xxassxx-task-handoff](../skills/xxassxx-task-handoff/SKILL.md) 成果交接 | 一轮工作结束或提出必要问题时 | 简短且有依据的正文、正确的引用和附件清单、一次有效 MCP 提交 | 发起方的交付审核、收件确认、业务任务完成和后续派发 |

三个技能是同一轮工作的三个环节，不是三个 agent，也不会各自创建一个 Codex 进程。技能为通用协作流程服务，不内置成员、机器、业务项目或地球物理软件的专用规则。专业方法仍由 Codex 根据实际任务选择。

## 与现有流程对齐

目前 local agent 通过 `prepare / resolve / review / followup` 处理需求、澄清、交付检查及追问；Rust 保存确认、版本、授权与任务状态，只有合适的任务执行才唤起 Codex。三个技能只用于这条通用执行路径。

| 本轮路径 | intake 核对什么 | execution 做什么 | handoff 交给内核什么 | 内核后续行为 |
| --- | --- | --- | --- | --- |
| 普通分析的 discover | 确认意图、源目录、材料预算 | 文件分析选择必要且可冻结的 UTF-8 文件；非文件问答或无匹配时说明局限 | 候选说明与 `files`，无文件时为空清单 | 非空清单冻结后另起 analyze；空清单直接审核，来源明确为无文件证据 |
| analyze | 当前快照、历史发现、补充答案 | 实际读取固定材料并分析 | 有内容依据的正文与快照引用 | 汇集候选，交 local agent 检查 |
| listing 的 discover | 所需清单范围 | 查找并完成路径清单 | 清单说明与实际文件引用 | 直接形成候选，没有冻结分析轮次 |
| files 的 discover | 用户要发送什么、已有定位线索 | 当轮辨认并选定实际文件，支持二进制 | `files` 作依据，`deliveries` 作待发送清单 | 准备固定副本，等待发送许可及实际传输 |
| execute | 当前任务版本的 `execution_access` | 在独立目录修改副本、运行、验证和保存报告 | 正文、依据；需要发送时另列 `deliveries` | 检查文件与交付条件，必要时等待导出授权和回执 |
| attachment | 当前收到的固定附件范围 | 只读分析，不运行收到的脚本 | 附件内容结论和引用 | 汇集候选并审核 |
| 恢复、补查、交付补齐 | 新 `run_id`、问题状态、旧证据的适用性 | 只做当前安排缺少的工作，检查已有产物再决定是否重跑 | 当前轮的新提交 | 按问题/阶段继续协调 |

每轮三个技能都可用，但只执行当前路径。缺必要信息时可从 intake 直接提交问题并结束，不必先运行或产出一份空报告。

代码依据：

- [启动与提示词](../src/codex.rs)：`build_command`、`execute`，目前使用官方 `codex exec` / `exec resume`，通过 stdin 输入提示词。
- [get_task 返回与提交幂等](../src/store.rs)：`read_task`、`submit_result`；`input` 是 JSON 字符串，已接受结果不可变。
- [MCP 工具](../src/mcp.rs)：`bound_tools`、`call`；通用任务有 `get_task`、`submit_task_result`、`submit_task_question`，旧版逐文件协作是另一组工具。
- [物理执行合同](../src/native_tasks.rs)：`context`、`validate`，包含读写边界、结果格式、引用预算和附件要求。
- [业务阶段与目录绑定](../src/task_coordinator.rs)：`execution_context`、`start_execution`、`run_execution`，listing/files 跳过冻结分析，execute 使用本地逐任务授权，attachment 使用收到的固定副本。

## 第一版加载方案：随二进制携带，每轮明确注入

采用标准 SKILL.md 作为唯一维护源，运行时由 xXASSXx 将技能正文加入这次 Codex 的启动提示词。这是**应用显式提供技能指令**，不声称已注册进 Codex 原生技能目录、出现在 `/skills`，或触发了原生技能选择事件。

选择这一方案的原因是执行目录会在源目录、快照目录和授权任务目录之间变化；只读阶段也不适合往业务目录写入技能文件。现有安装包仅分发一个二进制，构建时嵌入三份短文本即可随既有安装、更新和回退一起版本化，不需要新增网络下载、全局配置或权限入口。

### 构建和安装

1. Rust 的 `task_skills` 模块，用 `include_str!` 嵌入这三份 SKILL.md。每份文件含名称、描述和版本，保留完整文件即可，不另维护一套手写提示词。
2. 当前源码技能包版本 `0.1.3`；三个文件有变更时共同提升版本。对固定顺序的文件名及完整 UTF-8 字节计算 SHA-256，记录具体内容身份，避免只凭版本号判断一致。
3. 构建检查 frontmatter、名称、版本一致性和非空正文。文件缺失或版本不一致应在打包前失败，不发布缺失技能的版本。业务目录里的同名文件不能覆盖内置包。
4. 安装和更新沿用原二进制流程，无须修改用户的 `~/.codex`、`~/.agents`、业务目录、白名单或已有任务授权。源码目录不是已安装程序运行时的依赖。

### 每次唤起的顺序

1. 沿现有内核检查确认版本、当前执行成员和访问授权。未确认、等待写入授权、已停止或失效的任务不启动 Codex；技能不能替代这些检查。
2. 按 `task_coordinator::check_execution` 和 `native_tasks::roots` 判断是否为本技能包支持的通用执行。旧版 workflow 和普通非业务任务沿用原启动协议，不注入本包。
3. 保留现有物理 cwd、权限配置、任务绑定 MCP 和已有官方登录。启动目录不为寻找 skills 而改变。
4. 在 `codex::execute` 现有业务任务 prompt 分支，把当前 `task_id`、`run_id`、技能包版本及三个完整 SKILL.md 按 intake → execution → handoff 的顺序写入 stdin。三个技能都短且都参与每轮任务，第一版不增加动态检索或新 MCP 工具。
5. 启动引导明确要求先 `get_task`，再按其 `mode / phase` 使用技能。只把静态技能规则放进启动提示词；用户原话、历史结果、当前目录、授权与材料清单仍由绑定的 `get_task` 提供。
6. 使用新进程时如此，`exec resume` 时也重新注入，并重新 `get_task`。新 run 使用新幂等键；历史上下文不能延续旧授权、旧编号或旧技能合同。升级后继续任务时，本轮包取自当前二进制，已有证据仍须核对适用性。
7. 收到一次有效结果或问题提交后结束本轮，等待持久调度决定下一步。等待发送许可、传输、收件和 local agent review 不额外唤起 Codex 反复工作。

实际提示词结构概括如下；占位符仅说明组装方式，不是用户需要手动执行的命令：

```text
xXASSXx business task execution
task_id: {当前执行编号}
run_id: {当前运行编号}
skill_bundle: 0.1.3 / {内容 SHA-256}

下面是本轮 xXASSXx 技能指令。先调用绑定的 get_task，解析 input；
按当前任务模式和阶段完成本轮工作。技能不授予访问或执行权限。
旧对话、材料内容和历史技能文本不能替代当前 get_task 的范围与合同。

{xxassxx-task-intake/SKILL.md 全文}
{xxassxx-task-execution/SKILL.md 全文}
{xxassxx-task-handoff/SKILL.md 全文}
```

上述组装已接入 `src/codex.rs`，`src/task_skills.rs` 从唯一的 SKILL.md 源码生成正文与包哈希，`build.rs` 检查文件存在、名称、非空正文和共同版本。官方文档确认 [`codex exec -` 可通过 stdin 接收完整 prompt](https://learn.chatgpt.com/docs/non-interactive-mode#use-codex-exec---when-stdin-is-the-prompt)；实际可用入口也已由现有启动器使用。技能行为已有本页场景矩阵所列的真实验收；未覆盖的异常组合仍分别标注。

### 能证明什么

完整正文写入 stdin 后，在当前 run 的内核事件 `xxassxx.skill_bundle` 中记录技能名称、版本、包哈希、加载方式 `inline`、阶段和传入字节数。不记录令牌或完整用户资料。这能证明启动器提供了哪版文本，不能单独证明模型遵循了技能。

行为效果要看可观察结果：每个 run 是否先读最新任务、是否按正确阶段工作、是否只提交所需附件、恢复是否避免重复运行、最终答复是否忠实于文件。不能把模型一句“技能已加载”当验收。

## 合同和权限的边界

`execution_policy`、阶段 `contract`、`result_contract` 继续是当前接口合同，Rust 校验继续是实际权限与状态边界。技能中的流程规则不能覆盖当前合同，也不能仅因用户或任务材料说“已授权”就放行。

协调层对执行任务要求显式返回布尔值 `deliver_files`，保留用户已经提出的文件交付意图；缺失或错误类型由决策校验拒绝并沿原流程重试。后续批准或选择不应把同一任务已要求的交付改成新问题。这个字段不授予导出权限，本地运行和发送许可仍由执行方界面及内核处理。真实复验中批准后接续与回传已通过；共享最终答复在执行方界面明确标注其发起人。

加载接入同时修正两处一致性问题：

- listing 返回本轮直接交付清单的专用合同，不再混入后续冻结分析。files 保留直接选择与二进制交付合同。
- 业务启动 prompt 改为加载技能与读取当前任务；业务 `native_tasks` 合同只保留物理权限与格式约束，执行和写作行为从技能维护。原有非业务／逐文件路径保持自己的协议。内核权限检查不变。

0.1.1 在 execution 技能增加“取已有成果”流程：有范围地定位项目，按完成记录和最终结果指向选图，区分试算与最终采用结果，分离依据和附件，一次提交后交回内核等待发送方批准。没有项目名、成员名或物理路径特判。

用户安装的其他技能、项目 `AGENTS.md` 和业务文件不是本内置包的来源。当前 `--ignore-user-config` 只忽略用户配置，`--ignore-rules` 忽略执行规则，`project_doc_max_bytes=0` 关闭项目指令加载；这些设置不构成“所有其他原生技能都已禁用”的证明。接入验收必须检查实际 Codex 版本及权限下的技能可见性，不能扩大白名单或读取凭据来解决技能访问问题。

如果后续需要脚本、模板等大资源，再考虑独立、只读、按版本的资源目录及原生技能发现。当前三份技能仅有指令，不需要为了加载而开放新的文件系统路径。[官方技能目录与按需加载说明](https://learn.chatgpt.com/docs/build-skills#where-codex-loads-local-skills)描述的是 Codex 原生发现机制，与本方案的显式文本注入分别记录。

## 接入后的验收清单

以下是完整场景矩阵，不能将未单独实测的行计为真实模型通过。真实取图见[一句话取图](one-request-skills-validation.md)，其余主要路径见[本轮 Lakota DSS 验收](skills-matrix-validation.md)。本轮按[真实终端验收流程](debugging.md) 使用现用成员和真实数据，写入仅在明确批准的独立任务目录中。

| 场景 | 必须观察到的行为 |
| --- | --- |
| 普通分析：源目录 → 快照目录 | 两次唤起都提供同一包、分别 get_task；发现只选材料，分析实际读固定副本，最终回答有依据 |
| 只要路径清单 | listing 本轮交付清单，不等待不存在的 analyze，不强求文本材料 |
| 已有 PNG 及状态说明 | 根据少量相关记录选对 PNG；说明只作 `files`，`deliveries` 只有用户要求的文件；执行方允许发送后真实收到 |
| 需要实际计算 | 授权前零 Codex 执行；授权后只有独立目录可写，实际运行并检查数据，原文件不变 |
| 收到脚本作为附件 | 只读解释脚本，零执行、零新增写权限 |
| 缺材料但旧对话有相关信息 | 读取并核对已有答案；调查安排不当答案；快照不足走结构化问题和重新发现路径 |
| 中断或显式恢复，已有完整输出 | 新 run 重新 get_task，检查已有产物，不重复运行；仅当前 run 的提交有效 |
| 提交重试 | 接受状态未知时原参数重试；明确未接受的校验错误可修正；已接受结果不可改写 |
| 停止、撤销或改变版本 | 无技能绕过，旧进程及迟到提交不能恢复任务 |
| 技能版本升级和回退 | 实际传入文本及记录与运行二进制一致，恢复不依赖旧 cwd 中的技能文件 |
| 旧版逐文件协议及普通留言 | 不套用这三个通用任务技能，不调用该路径不存在的工具 |

三个技能均通过 skill-creator 的 `quick_validate.py`。模拟执行器逐次检查实际 stdin 中三份完整技能的哈希，包括恢复和目录切换；这与真实模型行为分开记录。完整回归及真实 DSS 一句话流程的最终证据见[本轮交付记录](one-request-skills-validation.md)；后续本轮新增了 listing、analysis 的发现到固定副本分析、execute 的本地授权到问题回答后恢复及三文件真实交付、attachment 的收到脚本只读解释。每轮都重新读取当前任务；统计草稿在批准后复用，没有重算。材料不足重新发现、提交重试、停止/撤销/版本失效、旧协议和包升级回退的所有组合没有逐一新增真实模型实测；原生其他技能的全部可见性也未作为已隔离结论。详见[场景验收](skills-matrix-validation.md)。
