## 真实终端与模型

用于升级起点的 `0.4.99-alpha` 是隔离验证版本：由最终 Rust 源码仅改包版本后构建，从未创建公开标签或 Release。目标是最终 `0.5.0-alpha` 包，真实 HTTPS 下载来自 Trader 临时静态目录，校验签名、哈希后安装。

**Mac / Apple Silicon**：真实 PTY 显示新版提示；在非默认新会话内先执行 `/identity`，空闲 30 秒后自动下载和安装、重启后台、重新打开原会话。再次 `/identity` 验证新界面响应。身份及完整配置、白名单、历史、原会话 ID 保持一致。随后在升级后的 TUI 发起、确认并完成实际文件只读任务 `0c2551a4-59e9-5019-809d-8292f6ea77e9`，真实 DeepSeek 与官方 Codex 执行 discovery/analysis 两阶段，均退出 0、确认 turn.completed。亲自查看最终界面中的数值和来源，任务显示完成、下一步无，退出后终端模式恢复。

两端读取同内容的 71 字节合成文件，原文件和快照 SHA-256 独立核对一致，且任务后原文件未变。没有通过 SSH 代做业务读取后再补造任务完成。SSH / Python 只负责隔离环境准备、PTY 按键、升级源托管和只读事后核验。

## Trader、HTTPS 和故障路径

在 Trader 使用独立安装和独立临时信箱：

1. 从真实 HTTPS 下载错误签名元数据，拒绝安装，旧程序哈希不变。
2. 下载长度不足的安装包，校验拒绝，旧程序哈希不变。
3. 独立信箱仍运行时，更新器在替换前被运行锁拒绝；旧信箱继续服务。
4. 管理员停止该测试信箱后，升级成功；手动重新启动，实际 `/v1/whoami` 返回的团队和成员目录与升级前一致。

另有模拟故障回归强制新版后台无法启动，验证恢复旧二进制及后台，保留数据库。没有把模拟回归写成真实模型或跨机业务故障。

Linux 首次本地构建曾因显式将 `musl-gcc` 用作 Rust 最终链接器而在 `_start_c` 崩溃。安装器的运行检查拒绝安装，日常程序未受影响。改为 Rust 默认链接器和仅用于 C 依赖的 musl 编译器后，最终静态包在 Lakota、Trader 均启动、升级通过。既有 GitHub CI 原本使用默认链接器，不需要这个覆盖。musl 构建仍有既有 `libc::time_t` 弃用警告，未将 Linux 构建表述为 Clippy 零警告。

实际 GitHub Releases API 检查成功，当前无高于 `0.5.0-alpha` 的已发布版本；未声称从 GitHub 下载了尚未发布的本版。签名发布工作流已接入，但第一次正式使用前仍需配置 Actions signing secret。
