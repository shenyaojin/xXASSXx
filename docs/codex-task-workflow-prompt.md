# 任务协作与工作目录改造实现提示词

请在当前 xXASSXx 仓库实际完成下述开发、迁移和验证。目标是让用户自己的 local agent 从需求澄清到结果归档持续负责一件跨成员任务，并使界面中的工作目录与实际执行上下文一致。本轮不开发 slash 命令。

先阅读 `AGENTS.md` 和 `docs/current-state.md`，检查当前 Git 状态，再查看相关源码。保留已有修改、数据和未跟踪文件，增量实现，不重新初始化仓库或个人端。这份提示词描述的是待实现需求；不要把它写成已交付能力。若历史阶段文档与本次用户已确认的流程冲突，以本次流程为准。

## 一 本轮目标和边界

xXASSXx 服务于少于十人的团队。Rust 内核负责持久状态、队列、边界检查和通信；local agent 负责理解用户意图、澄清、协调与汇总；实质性查找、读取、解释和分析尽量交给各成员自己的 Codex，复用其原生工具。

本轮完成工作目录语义修正、任务意图确认、统一任务卡、多轮协作、完成归档与重开、材料快照、定期任务会议、每日任务摘要，以及支撑这些功能的 TUI 和后台行为。执行范围继续限定为现有白名单内的只读任务，不新增修改业务文件、运行科研程序或任意远程执行的能力。

不实现 slash 分发、候选菜单、补全或任何新 slash 命令，包括 `/new`。会话数据层仍应支持独立新对话，并可在现有会话面板提供普通的新建入口；后续 slash 命令复用同一应用层动作。本轮也不实现 TG、自动更新、Windows、完整 Ollama 适配、文件同步平台或复杂角色权限体系。

先完成仓库实现和隔离验证，不自动替换 Mac、Lakota、Trader 上的常驻服务，不提交、推送或发布安装包。产出明确的升级与部署说明，部署留给后续单独执行。

## 二 用户已经确认的协作流程

用户 A → local agent A 复述需求 → 用户确认 → A 与 local agent B 协调 → B 调用 Codex B → 根据问题逐级澄清 → 持续多轮执行 → A 汇总并确认交付项齐全 → 自动归档和通知 → 用户可重开。

请完整实现以下行为：

1. 用户向自己的 A 提出任务。普通对话里的 `@成员` 表示希望让该成员参与，由 A 先接住意图；不是绕过 A，直接把原话发给对方执行。
2. 普通对话中发出 `@成员 正文` 时，内核立即幂等创建一张待确认的任务卡，再让 A 整理需求。普通本地聊天不必每句话建卡；明确进入任务委托时走同样的任务机制。
3. A 保留用户原话，另列整理后的目标、期望交付、参与人、已知约束和仍需澄清的问题。不得把模型猜测写成用户已经同意的要求。
4. 用户通过明确的确认动作或针对当前草稿的明确确认回复，确认该版本的任务意图。用户也可以修改或取消。确认前不得向 B 发送本任务的协作消息或启动该任务的 Codex；此约束必须由 Rust 状态检查保证，不能只写在模型提示词里。
5. 意图确认后，A 联系 B。B 根据本地实际能力和已配置范围接手，准备执行上下文并调用 Codex B，不再要求 B 的用户逐任务批准读取白名单内文件。
6. Codex B 可以返回结果，也可以提出结构化问题。B 先尝试用已知事实、本地配置或已有任务上下文回答；解决不了就问 A。需要复杂调查才能回答的，仍交给 Codex，不在 local agent 中重建工具链。
7. A 先检查已确认需求、已有对话和任务资料。能够回答就直接回答 B；仍缺少用户信息时，A 才向用户追加提问。一次尽量合并相关问题，不向用户暴露一串彼此重复的内部追问。
8. 用户回答必须关联原任务、当前任务修订和具体问题，再沿 A → B → Codex B 传回。中间回答不创建新任务，不要求用户重新描述目标。
9. A、B、Codex B 持续多轮往返。消息送达、Codex 一轮退出、MCP 提交成功和业务任务完成分别记录，不能相互替代。
10. B 返回候选交付后，A 对照最初确认的要求检查交付项、来源和未决问题。缺项则继续协调；需专业复核时可委托自己的 Codex A，不由 local agent 编造复核结论。
11. 满足要求后，A 整理最终结果、完成任务卡、归档并通知用户。默认不增加最终人工验收关卡。
12. 用户不满意，可以在已归档任务上重开，保留任务编号、历史过程、旧结果和旧快照，追加新修订继续工作。

“确认任务意图”与“批准访问文件”是两种操作：保留前者，取消白名单内新任务的逐次文件授权。

## 三 工作目录与独立对话

当前目录选择器的标题是“当前项目”，列出的却是本地路径。将这个面向用户的概念统一为“工作目录”。不要用它代表团队，也不引入额外的共享项目管理体系。

用户应该能分清：团队表示协作成员；工作目录表示本地默认工作位置；白名单表示可访问范围；对话表示聊天上下文；任务表示持续跟踪的工作。同一个工作目录可以有多段对话，同一个任务可以涉及不同成员各自不同的工作目录。

具体要求：

- 将目录选择面板、顶部状态、任务详情、提示和帮助中的相关“项目”用语改为“工作目录”。只改这一含义的用语，不全局替换所有技术术语或历史证据。
- 目录面板使用“选择工作目录”“选择”“输入其他路径”等明确措辞。去掉“同时允许所选目录导入”这种混合含义的操作。白名单由独立的“可访问目录”入口管理，复用现有入口。
- 首次选择尚未在白名单内的目录时，可保留加入白名单的询问；拒绝不授予读取权限，也不妨碍普通聊天。之后用户可从白名单入口修改。
- 每次请求都提供准确的当前工作目录、可访问目录和所选任务上下文给 A。A 回答“你在哪里、能访问什么”时依据这些事实。
- 新任务明确保存自己的工作目录和本地执行范围。普通原生文件任务实际使用该目录，禁止静默改成白名单列表中的第一个目录。
- 选中目录未获准、被删除或当前范围已失效时，显示具体问题，允许改选已有可访问目录或添加白名单；禁止自动扩大到父目录或整个 HOME。
- 入站任务的 B 使用自己保存的本地工作位置和可访问目录，明确记录本次绑定。A 不需要知道或指定 B 的绝对路径，双方路径不必相同。缺少可用配置时显示卡点，不假装执行。
- 切换界面工作目录只影响之后的对话和任务，不改变已经启动的任务上下文。进入旧任务时显示它绑定的目录，避免用户误以为它随当前界面一起切换。
- 支持同一工作目录内多个独立对话，保留旧对话。新对话不暗带旧聊天或旧 Codex 会话，不取消已有后台任务。进入任务卡后，显式加载该任务上下文。
- 当前 `app_sessions` 的 `(project_id, recipient)` 唯一约束需要适当迁移。无需为了改名大规模重命名内部表，但应用层语义必须一致。

## 四 统一业务任务与生命周期

不要继续让普通消息、`app_tasks` 任务卡、`native_tasks`、底层 Codex 执行和旧工作流彼此独立，靠“最近一次回复”猜关联。建立一份明确的业务任务身份和关系：一个业务任务可以关联多条消息、多个问题、多次执行及多个成员的本地会话。

至少保存以下事实，具体表结构自行按现有设计合理实现：

- 稳定的全局任务 ID 和便于显示的短编号；后者不得替代协议中的全局 ID。
- 发起成员及其 local agent A、参与成员、原始意图、整理后的目标和交付标准。
- 任务修订、确认记录、当前状态、等待对象与原因、下一步负责人和最近活动时间。
- 每个成员的本地工作目录绑定；对外使用合适的成员和材料引用，不强制共享本地绝对路径。
- 对话关联、执行记录、问题和答案、文件快照、候选结果、最终结果与通知状态。

采用以下用户可理解的生命周期；内部名字可以不同，但行为应一致：

| 状态 | 行为 |
| --- | --- |
| 待确认 | A 正在澄清或复述，尚未发送执行请求，用户可修改、确认、取消 |
| 待接收 | 已确认，请求持久排队，等待参与方真实接收 |
| 处理中 | 已接手，正在协调、执行、处理答案或检查交付 |
| 等待 | 显示正在等谁、等什么，区分用户补充、对方离线、执行结果或配置缺失 |
| 需要处理 | 达到重试限制、没有进展、执行结果不确定或无法继续，提供原因及恢复入口 |
| 已完成 | A 已生成有依据的最终交付，自动归档，通知持久保存 |
| 已取消 | 停止继续派发该任务工作，保留历史；正在运行的本地执行按现有能力协作停止 |

“归档”是保存与展示行为，不是删除。已完成和已取消的任务可从历史进入。用户主动重开时，追加修订并回到意图澄清或待确认流程；若同一次用户操作明确确认了新要求，也应记录该确认。

所有任务状态推进都由 Rust 校验合法转换。A 是最终汇总和完成判定的负责方，B 报告本地进度和候选结果；服务器保存可供参与者同步和调度的事实，不另设一个能与 A 互相覆盖的 LLM 决策者。

任务处于等待用户时，不能把“已发送追问”当作完成。Codex 提交问题不能把业务任务标成成功。旧修订的迟到回复、执行结果或会议消息不能覆盖重开后的新修订；应作为历史记录或明确处理。

## 五 多轮协议与恢复

复用现有团队信箱、消息和任务机制，补充必要的版本化消息类型。建议覆盖任务提议、接收、问题、答案、进展、候选结果、完成、取消、重开以及会议和摘要事件；名称不强制。

每条任务消息必须携带可靠的任务关联和幂等信息，包括协议版本、任务 ID、任务修订、消息 ID、发送者、接收者和必要的回复目标。提问和答复有稳定的问题 ID；执行有独立的运行或尝试 ID。参与成员身份取自现有认证结果，不能从正文自报用户名获得。用单调事件序号或等价的版本检查处理同一修订内的乱序状态更新，不能仅按网络到达顺序覆盖当前状态。

区分澄清回答与目标变更。回答当前范围内的事实问题可以直接续接；变更交付目标或参与范围时更新意图修订，并明确让用户确认，不能拿旧确认启动新的任务目标。

为 Codex 提供结构化的“需要澄清”和“提交结果”出口，可扩展现有 MCP 任务接口。问题要包含问题正文、为什么需要、已知信息和关联任务；不要靠正则寻找自然语言问号来判断是否需要续接。MCP 继续负责上下文和协作，不新增通用文件搜索工具来替代 Codex 原生工具。

收到答案后，恢复同一任务对应的 Codex 会话，提供具体问题、答案和新的有效上下文。不得把不同任务、不同修订或新对话串到错误的会话。官方会话确实无法恢复时可以依据持久上下文新建一次执行，但要记录原因和新旧关系，不声称发生了真实 resume。

沿用持久收发队列和幂等副作用，处理重复投递、断线重连和服务重启。去重、状态变化与待发送事件应具有一致的事务边界。不要宣称跨网络和模型调用天然具备 exactly once；对执行结果不确定的情况保留证据并显示需要处理，不能盲目重放。

同一 Codex 会话不得并发执行两轮。会议和新消息可入队，不中断正在运行的有效工作。设置可配置的自动轮数、重复无进展和重试上限；达到限制时显式停在需要处理，不伪造成功，也不让下一次定时会议绕过限制无限重试。

回复关联由任务和问题决定，不由当前 TUI 焦点或最近一个联系人决定。同时有多件任务等待用户时，应在任务卡中回答，或先明确选择任务，不能把一句“可以”广播给多个任务。

## 六 白名单与快照

保留现有团队邀请、成员身份校验、消息来源检查、目录白名单和执行范围。用户已经明确选择“取消逐次授权，保留自动身份校验”。不要移除公网信箱认证，不增加复杂的角色管理，也不要求每个文件、每轮读取重复弹确认。

新流程应在既有白名单内自动准备任务所需的材料。旧固定文件授权入口可为历史兼容保留，但不能继续成为新任务的必经步骤。白名单撤销、目录消失和路径越界必须在后续执行时得到处理；任务快照不应成为绕过白名单撤销的新访问通道。

实现两类可追溯记录：任务快照保存已确认目标、修订、参与者、问题、结论和结果；材料快照保存正式分析实际使用的文件内容及其成员来源、相对路径、版本或快照 ID、哈希、字节数和时间。

复用现有内容寻址或知识版本存储，避免重新造一个网盘。不能只存哈希而不保存所指内容，也不能在分析结束后复制当前文件，就宣称它是分析时读取的版本。

建议采用可实现的两步流程：先由 Codex 原生工具在白名单内发现候选文件，再由 Rust 固定相关材料，随后让正式读取和分析使用不可变的任务材料目录。快照不要求用户手工挑文件或提供 object ID。对于纯文件清单查询，明确记录搜索时间和覆盖范围；对候选内容的描述应依据后续固定版本的实际读取，不把先前实时搜索记录伪装成快照分析证据。

快照分析的物理执行目录可以是材料目录，但它必须明确映射回该任务的逻辑工作目录和来源文件，界面和模型上下文都能说明这一点。继续复用 Codex 原生工具，任务执行范围应确保它实际读取固定材料，而不是还能绕回实时源文件分析。

不自动复制整个 HOME、所有白名单目录或大型数据集。本轮优先支持只读脚本与文档，规定文件数和总字节上限；超限、二进制材料、复制中源文件发生变化或缺少依赖时给出明确结果或阻塞，不静默截断后声称完整分析。保持必要的相对路径关系，检查符号链接和越界。

材料默认保留在所属成员本机；信箱只承载必要的任务信息、结果、摘要和版本引用，不集中上传所有文件。重开任务时保留旧快照，若要使用新材料建立新快照并记录版本变化。归档不得默认删除证据。

## 七 定期任务会议

在团队信箱服务增加轻量持久调度能力，针对已确认且未结束的任务，定期邀请当前参与成员的 local agent 汇报和协调。固定周期检查是需求，不能替换成“只有出错时才通知”。不用操作系统外部 cron 或本次 Codex 聊天的自动化来充当产品功能。

默认配置先采用每两小时一次，每场最多两轮状态交流，等待窗口五分钟；这些是可修改的产品默认值，不是硬编码业务规则。测试应使用可控时间推进，无需真的等待两小时。

每个参与 agent 汇报已完成事项、依据、当前阻塞、下一步负责人和行动。A 汇总并更新任务卡。可以用已有持久状态回答的情况，不必重新启动 Codex；需要实际调查和执行时才委托。在线成员应参与，即使本轮没有新进展也应提交简短状态。

参与者离线时标记缺席或等待，上线后合并补报；不要声称能唤醒已关机的电脑。A 离线时其他成员的汇报仍可保存，最终协调结论等待 A 处理。任务正在等待用户回答时，保留准确问题，不让会议替用户猜答案。

会议必须有稳定 ID、任务修订、到期时间、参与名单和结果。重启、重复调度、多次拉取不能产生重复会议或重复执行。长期离线后的过期会议可以合并为一次最新检查，保留合并记录，不瞬间补发大量邀请。服务器生成的会议与日报使用明确的系统事件来源，不冒用用户身份，也不能让普通消息自报成服务端调度事件。

待确认、已完成和已取消的任务不召开执行例会；需要处理的任务只汇报卡点，不自动无限重试。完成或取消应停掉后续会议。会议中出现的 @ 和内部消息不得触发新任务卡。

## 八 每日任务摘要

信箱服务每天向各任务涉及的用户生成并投递摘要。每个用户收到自己参与任务的完成事项、当前进展、阻塞、下一步负责人和任务入口；不要默认把全团队所有任务发给每个人。

服务端以已持久保存的任务事实生成基础摘要即可，不能要求服务器保存所有人的模型 key 或业务文件。自然语言润色可以是可选步骤，但事实摘要的生成和投递不依赖某台个人电脑在线或模型可用。

配置团队时区和发送时间。本轮默认明确使用 `America/Denver` 每日 18:00，允许修改；不得直接继承 Trader 的系统时区。内部保存 UTC 时间，个人界面按用户本地时区显示。处理时区和夏令时变化，确保同一团队日期、同一接收人只投递一次。

日报标明汇总截止时间及状态更新时间，离线成员的信息显示最后已知进展，不推测今天已经完成什么。重启补发和离线收件幂等；不要补发大量历史日报造成刷屏，可合并为有明确时间范围的补报。

通知先通过现有信箱、应用事件和 TUI 展示，关闭 TUI 后仍保留到下次打开。任务完成通知、会议摘要和日报应可区分。为未来 TG 等渠道保留统一应用层事件，不开发 TG bot，也不把核心逻辑绑定到终端展示。

## 九 TUI 中的具体体验

普通对话始终由自己的 local agent 承接。`@成员` 指定协作对象，候选仍只有 local agent，没有其他人的 Codex。Tab 继续切换查看成员状态，不暗改接收对象。

任务卡显示标题、发起人和参与人、状态、最近进展、下一步负责人、等待对象、未决问题、所绑定工作目录及结果入口。任务详情能查看内部协作、执行、快照和会议记录，主聊天展示整理后的重要进展，不倾倒原始协议 JSON。

待确认任务提供确认、修改和取消入口。待回答的问题有明确的任务关联。已完成任务提供结果、历史和重开入口；取消和重试等动作也复用应用层，不靠 TUI 直接改数据库。

普通对话外部 @ 创建新的待确认任务；进入一张任务卡后的消息继续该任务。任务内联系另一个成员应扩展同一任务的参与者，并明确显示成员变化，不派生出无关任务。无需本轮实现复杂的单条消息多 @ 语法，但任务模型和会议调度应支持多个参与者。

输入区域明确显示“正在与自己的 local agent 对话”或“正在回复任务 T-xxx”，不要只用选中颜色暗示。新对话、查看其他人状态或切换目录不丢失后台任务。完成通知持久保存且去重，用户无需一直盯着界面。

## 十 现有代码衔接与迁移

- `src/native_tasks.rs`、`src/butler.rs`、`src/codex.rs`、`src/supervisor.rs`：原生委托、执行与续接。

- `src/team.rs`、`src/mailbox.rs`、`src/presence.rs`：消息、成员身份和团队信箱。
- `src/file_roots.rs`、`src/knowledge.rs`、`src/task_files.rs`、`src/workflow*.rs`：目录范围、现有快照和历史协作。
- `src/tui/mod.rs`、`editor.rs`、`presentation.rs`、`startup.rs`：界面与启动目录。

已知需要修正的现状：项目路径没有充分进入模型任务上下文；原生执行目录取第一个白名单；外部 @ 可以直接进入对方会话和普通消息发送；通用原生执行尚未统一到任务卡；当前原生文件引用校验不等于快照读取证明。请核实后针对原因改造。

个人数据库和信箱数据库都使用增量迁移。保留成员、联系人、白名单、模型与 Codex 配置、聊天、历史任务和来源记录。历史数据没有确认记录、快照或完整关联时，明确标为历史信息不足，不能补造用户确认、执行证据或完成结果。

对于迁移中的旧在途任务，选择明确的兼容续跑或显示需要处理的策略，保证不会迁移后自动重复执行。保存恢复方式和版本兼容说明。旧客户端不能理解新任务协议时，要明确显示不支持并停止错误派发，不能把协议正文当普通用户指令执行。

不要为了本轮更改正式成员 ID、联系人、邀请或凭据。修改配置时以数据库中的实际生效配置为准，只变更必要字段；不要用可能过时的配置文件覆盖运行设置。日志、文档和测试证据不包含密钥或邀请正文。

## 十一 验证要求

运行与改动相关的格式、构建和测试检查，补充真正覆盖跨轮状态和恢复的测试。不要为单纯的文案改名堆砌镜像测试，也不要通过削弱现有范围检查换取测试通过。

至少覆盖以下场景：

1. 在同一工作目录下创建两个独立对话；上下文不串，已有任务继续运行。选择的目录同时正确进入模型上下文和原生执行，多个白名单不会覆盖用户选择；切换界面目录不改变在途任务。
2. 普通对话 @ 自动产生一张待确认卡；确认前零任务协作消息外发、零任务 Codex 启动。修改草稿后旧确认无效，重复确认只派发一次。取消草稿不发执行请求。
3. B 可以解决的问题直接回复 Codex；B 不能解决但 A 知道的问题由 A 回答；只有双方确实缺信息时才向用户提问。每个答案关联正确任务和问题，至少两个同时等待的任务不串答案。
4. Codex 提问后的真实续接或受控恢复，产生第二轮执行；第一轮 `turn.completed` 或退出码 0 不触发业务任务完成。
5. A 发现结果缺少交付项时继续协调，齐全后自动完成、归档并通知。用户重开沿用原任务 ID、新增修订；旧结果和旧快照保留，迟到消息不污染新修订。
6. 重复投递、断网和重启后，卡片、执行、问题和通知不重复；不确定的执行结果不被伪造为成功；取消后迟到结果不能重新启动任务。
7. 白名单内任务无需逐文件批准；未获准目录不能读取，撤销和符号链接越界得到处理。保留成员认证与消息来源检查。
8. 固定材料后修改原文件，正式分析仍读原快照；新修订可以使用新快照。材料限制、复制中变化、缺失内容和来源校验失败有可见结果。
9. 用可控时间验证定期会议：正常发起、离线参与者、A 离线、等待用户、运行中 Codex、重启去重和结束后停止。会议不能递归生成任务或重复执行。
10. 日报按参与者分发、按配置时区生成，覆盖日期切换、夏令时、重启和离线收件。摘要中的完成、等待和最后观测时间必须来自实际任务事实。
11. 从包含旧会话、任务和配置的数据迁移，保留原记录，重复打开幂等；新旧协议不兼容时明确失败而非误执行。
12. 通过 TUI 实际完成确认、回复问题、查看结果、进入归档任务、重开和查看工作目录；退出界面后后台仍处理合法事件，重新打开能看到结果。

确定性测试可以使用模拟模型和 Codex。除此之外，做一轮明确标注为真实模型验证的隔离双端流程：两个独立个人端和数据库、临时团队信箱、真实 local agent 模型和官方 Codex；可在同一台机器上运行，不把它称为真实双机部署。

使用合成的小型脚本和说明材料，设计如下只读任务：用户让 A 请 B 找到适合某个实验目标的入口脚本，说明参数、候选差异和选择依据。A 持有一份必要背景，B 持有两种候选材料，另一个确实影响选择的信息只由测试用户掌握。不要在材料里嵌入“现在必须调用某工具”的答案指令。

验证真实链路经历意图复述与用户确认、A 到 B、B 到 Codex、至少一次必要追问、返回用户补充、Codex 后续执行、A 汇总归档、完成通知和重开。测试程序可以模拟用户确认和回答，但必须标注这些是用户动作，不能把它们宣传成 agent 自主推理。不可手工填数据库或代写 agent 输出冒充链路成功。

保存精简证据：任务及修订 ID、确认记录、消息与问题关联、执行与实际 resume 记录、原生读取和快照来源、最终结果、重开后的状态、会议与日报的去重记录。真实模型不可用时继续完成确定性验证，如实说明真实链路未验证及原因，不用 mock 结果替代。

## 十二 实施顺序与交付

先完成业务任务身份、状态机、会话迁移和工作目录绑定；再接通意图确认与 A/B/Codex 多轮；随后落实快照与执行来源；再完成 TUI、定期会议和日报。可以分批构建和验证，但不能把只换文案或只改模型提示词当作整轮完成。

常规实现选择自行判断并继续推进。只有必须由用户提供的业务信息或不可恢复的外部阻塞才提问。不要因为这份需求较大就只交一份计划。

交付代码、针对性测试、简短设计与迁移说明、用户操作说明及验证记录。更新 `docs/current-state.md`，区分已实现、已验证、已部署和仍有缺口的部分；历史阶段证据保持原样。记录可调整的调度参数和默认值，并说明哪些证据来自模拟、真实模型及真实机器。

最后用中文简要说明用户可以怎样发起任务、确认、回答追问、查看归档和重开，以及实际通过的验证、未验证的环节和后续部署步骤。本轮不增加任何 slash 命令。
