## 根因与修复范围

原流程把多种失败归到“执行遇到无法自动修复的问题”：材料发现阶段可以提交普通文件和受保护路径，建立快照时才整批失败；错误没有把具体拒绝项和可用材料反馈给执行 agent。用户仅重试会再次撞到同一边界。与此同时，执行方无法在原任务留下本机处理约束，聊天纠正可能被当成新任务，后处理失败也没有清楚区分已完成执行与尚未完成的检查。

本次修复让失败保留原因、已有成果和处理入口。发起方可以在原任务补充纠正、请求原执行方继续；执行方可以保存本机约束并恢复自己负责的步骤。界面说明处理成员、暂停原因和下一步，普通执行错误改为“执行已暂停，需要核对原因或调整后继续”，不再把未知错误直接描述成不可修复。

实现按材料输入、权限、模型配置、待答问题、执行结果不确定等通用原因处理，没有针对 MBA、Trader、某条用户消息或某个业务项目设置例外。

## 已实现的恢复规则

| 场景 | 候选实现的行为与边界 |
| --- | --- |
| 材料不可用 | 提交时预检，建立快照时再次检查。反馈逐项路径、原因、下一步、仍可使用的候选及预算；覆盖受保护路径、失效或变动文件、格式和数量/字节限制。任一候选被拒绝时不生成部分快照，也不把缺失范围伪装成完整成功。 |
| 材料纠正 | 结构化反馈直接返回工具调用并保存在任务上下文；执行 agent 可在同一任务更正清单。仅重新打开需要纠正的发现步骤，自动尝试有累计上限；耗尽后保留历史，等待用户明确允许有限继续。 |
| 私有材料与权限 | 私钥、应用状态等保护不因 Full access、补充或重试而放宽；不通过复制到其他目录绕过。材料拒绝与本机权限、数据库或存储故障分别处理。权限恢复入口会重新校验当前授权。 |
| 两端补充和继续 | 发起方补充发给原执行方；执行方的 `executor_constraint` 保留在本机原任务，不向其他成员发送原文或读取回执。普通补充只保存，不宣称已经恢复；明确“补充并继续”才同时请求恢复。 |
| 原任务与已有成果 | 保留任务版本、原始输入、运行历史和已有成果。结果检查失败恢复时复用成功执行结果；材料清单确实无效时才要求发现步骤纠正。对于结果不确定的外部操作，先核对，不盲目重放。 |
| 恢复操作的原子性 | 在数据库写事务内读取当前状态并校验版本、失败步骤、责任和权限。补充并继续失败时整笔回滚，不遗留补充、不增加恢复预算；重复请求幂等。跨端恢复绑定原失败步骤，过期请求不能解除后来出现的暂停。 |
| 问答、停止与权限 | 真正等待用户回答的问题须经回答流程处理，恢复不能清掉问题；协调或调查问题时发生的处理失败仍可恢复。停止、撤销执行分配、本机授权分别校验，补充或重试不能替代授权或复活已撤销的执行。 |
| 旧任务 | 显式恢复时重新检查当前已保存的材料清单，用结构化检查结果判断是否需要纠正，不依赖解析旧错误文案；不静默扩大旧任务授权。 |

材料路径的实现见 [task_materials.rs](../src/task_materials.rs)，恢复分类见 [task_recovery.rs](../src/task_recovery.rs)，任务状态与两端控制见 [task_coordinator.rs](../src/task_coordinator.rs)。

## 存储中断后的材料目录恢复

文件系统重命名与 SQLite 提交无法组成同一个原子操作。若材料目录已落盘而快照记录写入失败，旧流程会留下固定名称的孤立目录，后续每次恢复又被该目录阻塞。

现在恢复会在数据库写锁下先检查归属：已有合法记录则校验并复用；目录没有快照记录归属时，将原内容完整保留到独立 `orphans` 目录，并写入 `retention.json`，记录任务、版本、执行、快照、原位置和保留原因，再重新读取并建立有效快照。保留材料只是故障证据，不被直接采纳为已验证成果。若目录属于任何已有快照，则拒绝移动或覆盖。后续存储失败仍保留原执行记录，不能冒称已完成。

## 结论边界

本次目标是让已知材料边界和处理失败可定位、可纠正、可在原任务接续，并保留权限约束与历史成果。三轮已完成验证分别证明检查失败可复用成功执行、材料拒绝可在原运行中纠正、执行方可先保存本机约束再明确恢复同一任务。外部服务、存储、模型或业务要求仍可能无法完成；届时应明确说明原因、处理成员和可用动作，必要时等待用户决定。自动纠正有次数限制，也不承诺任意业务永不出错。原故障已在日常环境完成恢复；外部服务或实际业务缺口仍须按具体原因处理，不能用成功的有限验证承诺任意任务零错误。
