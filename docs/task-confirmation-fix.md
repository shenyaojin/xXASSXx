# 任务确认与成员目录逻辑修复

日期：2026-10-07。适用于所有成员的 schema 7 任务，未增加特定机器、仓库或科研主题的分支。

## 故障与原因

一项真实协作任务连续三次确认失败：local agent 将发起端物理目录写入草稿，确认时整份草稿直接进入消息正文，被既有绝对路径校验拒绝；事务回滚使任务仍显示待确认，接收端没有任务。普通聊天中的明确确认又被草稿分支当作修订。准备草稿的模型上下文还混入旧模型草稿、倒序聊天和未区分归属的本机目录，导致用户纠正远端位置后仍被追问本机位置。

## 通用修复

- 本机物理路径只用于本地目录绑定。准备草稿和发送任务消息时，递归转换已知本机工作目录、白名单及 home 前缀为带成员归属的 `member://` 引用；每个执行成员仍由自己的真实目录和白名单校验权限。这些引用不授予访问能力，也不能作为另一台机器的路径执行。原始用户文本与历史草稿留在本机，既有消息路径校验保留。
- 模型上下文明确区分本人成员、本机资源和执行成员。准备草稿只取用户原话与补充事实，按时间顺序提供近期对话；不再把旧模型草稿作为既定需求。未知远端路径由执行方在已授权范围内发现。
- 明确的文字确认经应用入口保存对应修订，再由 Rust 执行确认。重复确认幂等，队列中滞后的确认不能确认新修订。少量明确表述按命令处理；含否定、附带修改或含糊表述不作授权推断。
- 确认失败记录到任务卡，保持可重试状态；确认成功清除该错误。旧草稿可经新的传输边界派发，不要求删除任务或历史。

## Linux 沙箱兼容性

真实跨机器验收继续发现 Linux 上 `bwrap` 启动失败：同时拒绝目录和该目录内的密钥文件，导致它在已封闭的父目录中创建子文件挂载点。合成探针在窄目录授权和较宽目录授权下均可稳定复现。

启动配置现在归并被父目录完全覆盖的重复拒绝项；若父目录内有重新开放的可读子目录，仍保留其中必要的私有文件拒绝。可读根目录与网络设置不变，未降级到宽松沙箱。实际探针确认正常文件可读、私有文件不可读、越界读取失败、写入失败。规则含义参考 [官方权限说明](https://learn.chatgpt.com/docs/permissions)，这个具体错误及修复结论来自 Lakota 实机探针。

## 材料预算与恢复

继续实机执行时，发现候选已被 MCP 接受，但总量超过快照预算，冻结阶段才报错。现在 `get_task` 提供当前文件数/字节预算和选择原则；发现阶段提交时校验预算，拒绝后同一执行可缩减候选重新提交。复制时的检查仍保留，以覆盖提交后文件增长等变化。

显式恢复会区分物理执行成功与业务处理成功：对已提交但后处理失败的执行重新排队并续接原会话，旧 run 的已接受结果保持不可变；不会无限重复冻结同一份错误结果。恢复原因进入当前执行上下文，并向参与方发送恢复状态。未调整本次的材料上限或白名单。

分析阶段提出补充材料时，旧逻辑的 `investigate` 仍续接仅能读取旧快照的会话，无法发现缺少的源文件。现改为事务内切换到新的发现执行，再生成新快照和分析会话；旧分析标为历史，原快照与 run 保留，问题关联到新执行。材料范围变化不冒充同范围 resume。协调器取得问题对应的执行阶段，并明确区分事实答案与待调查指令；只有实际 Codex 结果才将调查标记为已回答。已有白名单、文件数和字节预算不变。

协调上下文分别给出原绑定源目录与当前快照范围，不能从「快照缺失」推断「源目录越权/不存在」。新的物理执行接收前序已接受 run 的结果、覆盖范围和限制及其来源 ID，避免新会话丢掉发现依据。这是已记录的发现证据，不是访问旧范围的权限，也不把路径发现当成固定内容分析。

## 回归

Mac 完整回归 104 项通过，2 项旧 opt-in 测试默认忽略；Clippy 和格式检查通过。Lakota 的权限归并、迁移、协作、调度回归 20 项通过。

此前漏测的原因是验证范围不完整：初版真实模型闭环在同一台 Mac 的隔离双端完成，部署检查只证明迁移、界面、鉴权与在线状态。模拟草稿没有覆盖模型回显本机路径，Linux 没有执行真实沙箱，材料超限测试也没有串起「提交被接受—冻结失败—恢复原会话」的完整流程。服务在线、MCP 接受和进程退出成功均不能代替业务交付验收。

新增测试刻意让模型回显本机绝对路径，经过正常应用确认和实际 HTTP 信箱，验证另一成员收到任务并绑定自己的目录；同时覆盖文字确认、重复确认、旧修订确认、含糊/否定文本、已有路径草稿与历史保留。测试使用不同成员、不同工作目录，不依赖实际业务目录。

材料补充回归从缺少一个脚本的快照开始，执行结构化追问、真实 MCP 提交、重新发现与冻结、返回带来源的候选。测试在两次冻结之间修改源文件，断言旧快照保持原内容、新快照反映新内容，并验证阶段切换使用新会话、白名单和预算未扩大。

修复已安装到 Mac、Lakota、Trader，schema 仍为 7，未创建备份或扩大白名单。[修复及实机证据](task-confirmation-fix-evidence.json) 保存当前构建哈希、服务状态、原任务执行/续接、快照和未完成状态。

## 原任务实机验收边界

原任务经 Mac→Trader HTTPS 信箱→Lakota 实际执行，使用 DeepSeek 和官方 Codex CLI 0.159.2。文字确认送达、Linux 只读发现、材料预算恢复、原会话续接及补材料阶段切换均已实际运行。首次合格快照为 40 文件、880908 字节，后续重新发现形成 22 文件、454280 字节快照，并以 3 文件、25371 字节快照核实引用路径与读取边界；材料仍保留在 Lakota。

执行证据进一步确认：脚本中的 `parents[2]` 将 MOOSE、fibeRIS 和验证输出的引用定位到 `scripts` 上级项目目录，现有白名单只有 `scripts`。这只是实际引用和读取边界证据，未在白名单外验证文件存在性。原任务尚无完成结果/归档，已向用户提出是否将项目根目录加入只读范围，或按现有材料交付清点与缺口；收到选择前不扩大权限、不修改交付范围。长时间离线和完整业务结果质量也不由本轮测试代为保证。

## 后续实用性修复（2026-10-07）

用户随后发现补查回到 Mac、本机聊天内容与输入目标不一致，以及“要我回答什么”被当作事实答案。根因是执行成员按当前机器而非固定发起人计算，investigate 在本机直接创建执行；TUI 按会话混排消息并提前停止跟踪命令；有待答问题时将任意聊天强制改为 answer_task。这些是通用控制流错误，不是 MOOSE 特例。

另一个真实扫描已在 Lakota 完成发现，分析 23 份材料时被旧的 180 秒限制中断；发起方只显示等待，重试没有发回执行方。已增加远程显式恢复和更直接的状态提示，新配置默认每轮 600 秒。新旧状态、成员边界、继续补查、重试、界面任务绑定、普通聊天与回答分离均加入回归。确定性完整回归 106 项通过，2 项旧 opt-in 测试忽略；后续措辞与进展通知调整的 17 项任务回归也通过。后续终端验收发现简短追问仍收到冗长旧记录、部分输出双重转义换行；进一步缩减追问上下文并使用单独的用户说明提示，显示时修复普通文本段落且保留原始证据与代码转义。最终完整回归 107 项通过。

### 本机终端实际完成

实际操作安装后的 xXASSXx：选任务、重试、修改原任务要求并确认、等待 Lakota 返回结果、追问更简单的解释。扫描任务保留原超时 run，并续接同一 Codex 会话，完成了 23 份代表性材料的代码结构概览。原 MOOSE 任务在同一编号修订 5 中完成，Lakota 查找后读取/检索材料，返回当前进展、文件依据、未验证事项与下一步；本轮没有本机文件执行、没有新的用户问题、没有扩展目录权限。两端都记录完成和归档。

执行结果有真实内容：识别建模、观测对比、反演流程以及合成算例收敛日志；将现场报告的数值与本次能核实的证据分开，并指出后续应核对数据、输入、日志和误差定义。查看 32 份候选材料不等于整个 scripts 目录的文件总量。不能据此声称现场模型已验证。完整任务证据、终端屏幕与后续问答保留在 `smoke-output/terminal-routing-validation/`。

后续处理同类问题先运行 `cargo test --test task_workflow --test app` 复现控制流与界面，再做一次完整回归和必要的实际终端验收；实测发现的问题集中处理。不要再把 A 本机补查写成跨成员任务的预期行为，也不要只验确认派发与进程退出，而漏掉用户最终看到的任务、答案和措辞。
