# 成果交接

在本轮工作得到可提交结果、或确定必要问题之后使用。当前 `get_task` 的 `result_contract` 决定格式。一个 run 只接受一个结果或问题；交接完成后把控制权交回 xXASSXx。

## 写给接手者的内容

结果正文先回答原问题，说明实际做成或查明了什么，再给支持结论的必要依据和局限。默认使用用户的语言和两三段短文；计算结果只突出少量有意义的数值及含义，详细参数和运行记录留在执行报告里。用户明确要求详细报告时遵从其要求。

区分发现材料、完成分析、程序运行、文件待发送和收件完成。只陈述本轮能证实的状态；选定文件不能写成已送达，MCP 接受不能写成业务任务已完成。普通回复不讲内部编号、快照、根目录索引或模型调用过程，不擅自把模型坐标轴解释成地理方向。

说明尚缺什么及需要谁决定，仅使用本轮已知责任；未知时交回协调，不替其他成员作承诺。不自动创建下一项任务或继续跨成员交接。

## 按当前协议提交

结果通过 `submit_task_result` 提交。外层包含当前执行 `task_id`、`run_id`、`idempotency_key` 和 `result`；`idempotency_key` 使用当前 `run_id`，`result` 是 **JSON 编码的字符串**，不是直接嵌套对象。

`result` 解码后的结构为：

```json
{
  "body": "有事实依据的答复",
  "files": [{"root": 0, "path": "relative/evidence.txt", "reason": "支持哪项判断"}],
  "deliveries": [{"root": 0, "path": "relative/output.png", "reason": "用户要求的产物"}]
}
```

上例仅说明形状，不是待提交的文件。按真实结果填写：

- `files` 是依据引用，始终提供此数组；允许为空的场景以当前合同为准。普通分析的发现阶段需提供可冻结材料，快照分析需引用实际使用的当前快照文件。
- `deliveries` 是要求发送的附件；`mode=files` 或 `mode=execute` 且 `deliver_files=true` 时必填且非空。Ask for approval 的执行任务仅交付授权任务目录内产物；Full access 可交付本机所需文件，按当前 attachment_policy 判断。其他情况下省略；不要把全部依据自动转成附件。
- `root` 对应本轮 `authorized_roots` 索引，`path` 是该根下的真实文件相对路径。不得使用绝对路径、`..` 或其他成员的路径；正文及理由中也不输出本机绝对路径。不要额外塞入当前格式未支持的状态、成员或哈希字段。
- 当前限制为每个清单最多 40 项、正文最多 12000 UTF-8 字节、每项理由最多 1000 字节，整体结果最多 24000 字节；发现阶段另遵守材料预算。优先保留完成交付所需内容。

必要问题改用 `submit_task_question`，填写当前任务/run、相同的幂等键及 `body`、`reason`、`known`；不要把问题伪装成成功结果。没有找到合适的待发送文件时，提交问题，不能拿不相关文件补位。

## 提交后

明确接受后立即结束本轮，不再改写已接受结果、继续运行或等待附件送达。请求结果未知时只能用完全相同的工具参数重试；若工具明确校验拒绝且尚未接受，可以按具体错误修正后再交。停止、版本失效或授权撤销时不得重试绕过。

最终用户答复、附件发送授权、传输回执和业务任务完成，由 local agent 与内核依据真实记录处理。Codex 的最后一条自然语言消息不能替代 MCP 提交。
